# 0027. atoom 0.7.0 and `--audit-scope`: the key drivers are told no installation

Status: accepted, 2026-11-25 (owner decision D48); partly supersedes [0024](0024-audit-transport-is-an-explicit-switch.md) (the row `--environment` and the consequences that name it: the flag is now `--audit-scope`, and no driver is told it)
Date: 2026-11-25

Carries out what the Open line of [0024](0024-audit-transport-is-an-explicit-switch.md) recorded as decided, in the change that moves session to atoom 0.7.0. It keeps every other rule of 0024 and of [0023](0023-audit-emitter.md): exactly one of `--audit-socket` and `--audit-stdout`, and the scope of the log a name only.

## Context

Until atoom 0.6.0, the software key driver took the name of an environment (unset, `development`, `staging` or `production`) and refused any other value; session passed it the value of `--environment` verbatim, the same flag that named the scope of the audit log. atoom 0.7.0 (atoom record 0021, "drivers know no deployment shapes") removes the environments from `key/software` and `key/yubikeypiv`: a driver opens its keys and nothing more, and a host that must not use file keys in some installation does not mount the driver there.

session never turned on the software driver's production floor (`RefuseProduction`): the driver checked only that the name was one of its four. So nothing session refused before is lost with it.

With no driver to tell, the flag names one thing only, the scope of the audit log, and its name says less than it should.

## Decision

| Subject | Choice |
| --- | --- |
| atoom | Every atoom module at 0.7.0, one version, as before. `spike/` keeps the pins it ran with |
| The key drivers | session tells no key driver an installation. `atoomx.KeyOptions.Environment` and the environment argument of `atoomx.SoftwareKeys` are gone, and so is `Environment: "development"` in the tests |
| File keys in a deployment | A deployment that must not hold keys in files puts every purpose on AWS KMS with `--key PURPOSE=awskms[:KEY]` ([0019](0019-signing-keys-on-aws-kms.md)); the software driver is then not mounted, and `--key-dir` is not needed. session adds no guard of its own: a guard would decide by the name of an installation, which session does not know |
| The flag | `--environment` is renamed `--audit-scope`, a breaking change at start-up. It is the scope of the log (`metadata.log_name`, `actor.user.uid` `session@<scope>`), the label `local` when unset. Nothing in session decides by its value. `--environment` is no longer a flag: a deployment that passes it fails to start |
| The correlation header | atoom 0.7.0's clients send `Atoom-Correlation-Id`, as [0006](0006-built-on-atoom.md) planned; its servers also read `Sluis-Correlation-Id` for the 0.7.x releases. session reads neither header itself, so nothing in session changes |
| The audit emitter | `truvity/audit/emitter` stays at 0.19.0. It asks for atoom 0.5.0; the build selects 0.7.0, and the emitter's tests and the conformance suite pass against it |

## Consequences

- A deployment renames `--environment X` to `--audit-scope X` when it moves to this version. Its records keep the same scope.
- `--audit-scope local` and every other value now work with a purpose on the software driver: no driver checks the label.
- A start-up guard against file keys, if a deployment ever wants one, is a neutral switch such as `--key-drivers awskms` (refuse any other driver); it is not built, because the first sites put their keys on KMS by `--key` ([0025](0025-first-version-for-the-first-sites.md)).

## Roads not taken

| Road | Why not |
| --- | --- |
| Keep `--environment` as a deprecated alias of `--audit-scope` | session has no release yet and no deployment; an alias keeps the old name's meaning alive for nothing |
| `--log-scope` or `--scope` | `--audit-scope` says which log, beside `--audit-socket` and `--audit-stdout` |
| Refuse the software driver when `--audit-scope` is set | A policy chosen by a label, what 0024 removed |

## Open
