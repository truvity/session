# 0036. atoom 0.9.0, audit 0.21.0, and session's AuditCatalogue

Status: proposed, 2026-11-26 (the owner's D118 A moves session to atoom 0.9.0 and audit 0.21.0 and has session publish its own catalogue; C1 to C3 below wait for the owner)
Date: 2026-11-26

The number 0035 is taken by the open pull request of the `idp` claim, so this record is 0036. It closes the open point of [0023](0023-audit-emitter.md) "publishing session's catalogue", and keeps every rule of [0024](0024-audit-transport-is-an-explicit-switch.md) and [0032](0032-atoom-0.8.0-transports-and-the-appconfig-source.md).

## Context

- **atoom 0.9.0** makes the transport message generic ([atoom record 0025](https://github.com/truvity/atoom/blob/v0.9.0/docs/decisions/0025-generic-blob-transport-and-index.md), step B12): `AuditMessage{uid, record, usage}` is `Message{id, payload}`, with the field numbers 1 and 2 kept and 3 reserved, so the bytes in a spool, a JetStream stream or an SQS queue read the same. The refusals of an empty message name `message.id` and `message.payload`. The constructors of `transport/nats` and `transport/sqs` do not change.
- **audit 0.21.0** moves the emitter to atoom 0.9.0. It builds `Message{id: uid, payload: record}`, the payload being the bare record, so records do not change.
- **audit's writer quarantines every record of a project that has no catalogue** ([audit record 0020](https://github.com/truvity/audit/blob/v0.21.0/docs/decisions/0020-the-writer-moves-here-first-and-reads-nats-jetstream.md)). Until atoom's `state` block exists it reads the signed documents `AuditLog` (`audit-log.jws`) and `AuditCatalogue` (`audit-catalogue.jws`) through the source port. 0020 puts session's catalogue on session: its table and schemas are code here (`internal/audit`), and they must reach the writer before the first records do.
- **The kind's exact field names are open in audit.** audit's reference ("Action table and catalogue", "Configuration kinds") lists four parts: `release`, `policy`, `table` and `schemas`. They will be fixed as `audit.config.v1alpha1` with the writer's move. The only reader that runs today is sluis's writer, whose kind (`sluis.config.v2alpha1.AuditCatalogue`) has `release`, `actions` (only the names), `schemas` (a list of `name` and `json`) and `policy`. That kind also requires each action name to be two or more lower-case words joined by dots, and session's names (`sign-in`, `token-exchange`) have hyphens. audit's emitter and table format only require a name to be unique.

## Decision

### atoom and audit

| Subject | Choice |
| --- | --- |
| atoom | Every atoom module at 0.9.0, one version (`go list -m all` lists only 0.9.0). `spike/` keeps the pins it ran with |
| The audit emitter | `github.com/truvity/audit/emitter` 0.21.0 (tag `emitter/v0.21.0`), on atoom 0.9.0 |
| Code | `internal/audit.Lines` reads `Message.id` and `Message.payload` and refuses with `message.id` and `message.payload`. The `--audit-nats` and `--audit-sqs` switches do not change. No flag, record or behaviour changes |

### The catalogue

| Subject | Choice |
| --- | --- |
| C1, the form | The payload of the signed document is a JSON object with one item, `default` (the kind is a singleton for each project, audit record 0015). The item has audit's four parts: `release`; `policy`, the schema policy's version (the emitter's `PolicyVersion`, 1); `table`, session's table in the keys of audit's table format (`ocsf`, `product`, and `actions`, where each row has `name`, `actor`, `class`, `activities`, `outcomes`, `subject`, `policy` and `fields`); and `schemas`, a list of `name` and `json` holding the shared definitions and one schema for each action. A schema is JSON text, the bytes the schema policy checked, as sluis's kind keeps it |
| C2, the action names | Kept: `sign-in`, `logout`, `back-channel-logout`, `denied`, `token-exchange`, `refresh`. They are `metadata.event_code` of every record, and audit's format requires only that each is unique. audit's `AuditCatalogue` kind should not take on the dotted pattern of sluis's kind |
| C3, where it lives | Made by `session catalogue [--release V]`, which is in the binary and the image. The release defaults to the binary's own version. The command refuses a release that is not a semantic version, and refuses a table or schemas that a writer would refuse at its start. The committed catalogue is `deploy/audit/audit-catalogue.json`, for the release `0.0.0`. Every build before the first tag is a pre-release of 0.0.0 (`0.0.0-dev`, `0.0.0-master.<commit>`), so it covers them. `just catalogue` writes it, and `just check-catalogue` (in the CI job `lint`) fails while it differs from what the table makes. A unit test holds the same rule and validates a record of every action against a table rebuilt from the catalogue alone |

### How it reaches a writer (the deployment's work)

Nothing of this is built here.

1. **Make** the payload for the release being deployed. Use the committed file for a `master-<commit>` image. For an image `X.Y.Z`, run `session catalogue --release X.Y.Z` from that image.
2. **Sign** it as the kind `AuditCatalogue`, in the signed config format that atoom's policy loader verifies: a JWS in the general JSON serialisation with the protected header `{"alg":"ES384","kid":"<the publisher's pinned name>","seq":<n>,"kind":"AuditCatalogue"}`. Raise `seq` with each new catalogue.
3. **Publish** it as `audit-catalogue.jws` in the source of the writer that serves session's project: its `--config-dir` directory, or its AppConfig profile. Do this **before** the image of that release emits. A record of a release newer than the catalogue's is quarantined.
4. Within a major version the table only grows, so the newest release's catalogue covers every older release, and one document per project is enough.

## Consequences

- No record, flag or wire byte changes. A spool, a JetStream stream or an SQS queue written by 0.8.0 reads the same.
- A change to the table without `just catalogue` fails CI, so the committed catalogue is always the table's.
- The catalogue follows audit's documented parts, not sluis's kind. If `audit.config.v1alpha1` fixes other field names, only `internal/audit.Catalogue` changes; the table and the records do not. Until then, no reader that runs today takes the document as it is. sluis's writer wants `actions` and refuses hyphens, and it serves sluis's project, not session's.
- `just test-nats` checks the renamed message: the record that lands is `Message.payload`, under `Message.id`, and a retry is one message.

## Roads not taken

| Road | Why not |
| --- | --- |
| C1 B: sluis's kind (`release`, `actions`, `schemas`, `policy`) | It is the one reader that runs, but it serves sluis's project. Its name pattern refuses session's actions, and audit is writing its own kind from the four parts of its reference |
| C1 C: audit's parts and an `actions` list as well | A strict reader refuses a field it does not declare, so a superset is accepted by neither kind |
| C2 B: dotted names (`session.sign_in`, ...) | It changes `metadata.event_code` in every record to fit one reader's validation rule. audit's own table format does not ask for it |
| C3 B: the catalogue only as a GitHub release asset | session has no release yet. The binary makes the catalogue of its own release, so a deployment has it wherever it has the image. An asset can come with the first tag |
| A YAML catalogue, as sluis commits one | The signed payload is JSON, and JSON leaves a single way to read the file |
| Generating the catalogue with audit's generator | audit's generator has not moved to `truvity/audit`. session's table is code (0023) |
| Signing in this repository's CI | The publisher's key and its pin belong to the installation, and CI never publishes |

## Open

- The exact field names of `audit.config.v1alpha1`'s `AuditCatalogue`, when audit fixes them; `internal/audit.Catalogue` follows.
- audit's rule for a change ("CI compares the new table with the previous release's and fails on a breaking change"): it needs a first release to compare with, so it comes with `v0.1.0`.
