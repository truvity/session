## 2. Item 1: the check core on atoom drivers

### 2.1 Method

Code: `spike/internal/fit` (`store.go`, `keys.go`, `source.go`, `memnet.go`, `env.go`, `counting.go`, `bench.go`), tests in `fit_test.go`, the benchmark `spike/cmd/fitbench`. The first spike's `Core` takes a `CheckStore`; its own `Store` and the new atom-backed `fit.Store` both fit it. `fit.Store` calls `atoom.store.v1alpha1.ItemService` through the generated ConnectRPC client. The driver `store/dynamodb` is mounted on an in-memory transport exactly as `socket/docs/in-process.md` shows for Go (a listener of `net.Pipe` pairs, `call.Inherit` around the handler, `call.ClientOptions()` on the client). The DynamoDB client under the driver is wrapped, to count the DynamoDB calls each contract call makes. The record is sealed with the first spike's AES-GCM, because atoom's `seal` block is not on master.

The value of an item is a 16-byte readable header (creation in milliseconds, last seen) followed by the sealed record. The absolute lifetime is the item's `expires_at`. The key is `S#` and the keyed hash of the id.

`key/software` and `source/file` are mounted the same way. The key port signs the `private_key_jwt` assertion. `source/file` reads the site file and watches it.

### 2.2 Latency of the check read

`spike/results/fit-bench.txt`. One caller, sequential, 5 rounds of 3,000 calls for each path, the paths taking turns, so a drift of the machine hits all of them. DynamoDB Local, same host, load average about 1. Times in milliseconds. **This is not the latency of the real DynamoDB service.**

| Path | n | mean | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- | --- |
| `GetItem` strong + decrypt, AWS SDK direct (first spike's path) | 15000 | 0.239 | 0.208 | 0.392 | 0.565 | 4.790 |
| `Get` linearizable + decrypt, atoom store port in-process | 15000 | 0.330 | 0.293 | 0.551 | 0.833 | 3.257 |
| The port's transport alone (stub driver, no DynamoDB) | 15000 | 0.064 | 0.048 | 0.138 | 0.390 | 1.188 |
| `Core.Check`, direct store | 15000 | 0.231 | 0.208 | 0.372 | 0.583 | 3.827 |
| `Core.Check`, atoom store port in-process | 15000 | 0.323 | 0.290 | 0.533 | 0.836 | 4.090 |

Three earlier runs on the same machine (not saved; same code, 2,000 or 3,000 calls for each round) gave 0.216, 0.208 and 0.216 ms for the direct path against 0.276, 0.263 and 0.305 ms for the port at p50, and 0.552, 0.557 and 0.504 against 0.834, 0.723 and 0.811 at p99. So the in-process port adds **0.06 to 0.09 ms at p50 and 0.2 to 0.3 ms at p99** here. Of that, the port's transport alone is 0.05 ms at p50 (Connect framing, protobuf, the `net.Pipe` hop, the handler), and the rest is the driver's own work (it builds the DynamoDB request from the contract's key and flags and decodes the item back).

The throughput of concurrent callers on the same host (`fit-bench.txt`, second table): at 8 callers 15,346 reads a second through the port against 18,442 direct, with p99 1.53 ms against 0.81 ms. At 32 callers 19,025 against 22,189, with p99 5.45 ms against 2.97 ms. Most of the time is DynamoDB Local's Java process, not the port.

What this says: the port is a fixed cost of a few tenths of a millisecond at most. A call to the real service takes milliseconds, so the port is a few percent of a check, but the number that matters is the real service's. It is in section 4, part C of the script, run from inside the region.

The calls the driver makes for each contract call (the test `TestCheckCoreOnAtomStore` and the others in `spike/results/fit-tests.txt`):

| Contract call | DynamoDB calls |
| --- | --- |
| `Get`, linearizable (the check) | 1 `GetItem` with `ConsistentRead`. 1 read unit for an item under 4 KB |
| `Transact` with one put and the key absent (create an item and its two index entries) | 1 `BatchGetItem` (a strongly consistent read of every key it touches), then 1 `TransactWriteItems` |
| `Transact` with one put under a version condition, no index change (idle refresh) | 1 `BatchGetItem`, then 1 conditional `PutItem` |
| Eight refreshes at one version | one winner, 15 `BatchGetItem` and 8 `TransactWriteItems` in all |
| `Query` by index, linearizable, then the delete | `Query`, `BatchGetItem` of the items it names, then the delete is `BatchGetItem` and `TransactWriteItems` |

### 2.3 What fits and what does not

Each point says what `session` needed, what the contract gave, and what was tested.

**2.3.1 Index entries for the logout lookup: fit, and better than pointer items.** [0010](decisions/0010-logout-pointer-items.md) chose pointer items (an item per `sid` and per subject holding a set of session keys, written in the session transaction) because a global secondary index is eventually consistent. atoom's index entries are items of the base table, written and deleted in the transaction of their item, and `Query` by index takes `linearizable: true` ([store/dynamodb/docs/layout.md](https://github.com/truvity/atoom/blob/94ab004a41171fd74f8c9c37bbb832595324d6dc/store/dynamodb/docs/layout.md), "Reads and linearizability"). So the lookup 0010 builds by hand is a contract feature:

- A session is one `Put` with two `IndexEntry` values, `sid` = `issuer|sid` and `sub` = `issuer|subject`. A logout is `Query{index, index_value, linearizable: true}` and one `Transact` of deletes. Tested: a session is found at once after its creation, a logout by `sid` deletes only that session, a logout by subject deletes the rest, and a deleted session leaves no entry.
- No read-modify-write. Sixteen parallel sign-ins of one subject: with index entries 0 failed, 16 tries in total, 21 ms. With pointer items (`CreateWithPointers`, one version condition on each pointer) 0 failed but 64 tries in total (each lost race reads and tries again), 123 ms. With more sessions for one subject the pointer item also grows towards the 400 KB item limit that 0010 mentions. Entries have no such limit.
- The cost: a logout by index is a `Query` plus a `BatchGetItem` of the items, against one `GetItem` for a pointer. Logout is rare. Creation writes the same three items either way.
- Unchanged: the tombstone read at creation, which closes the race of a logout that arrives before the sign-in has finished, is still needed.
- DynamoDB Local does not show the difference between a strongly and an eventually consistent read. The claim that the query cannot miss a committed session is the driver's documentation, not something this spike observed.
- A trap: an item's `Put` must send **all** its index entries again. A put that leaves one out deletes it. The idle refresh does this (`fit.Store.Touch`); the test checks that the entries survive a refresh.

**2.3.2 Conditions: enough, but no partial update.** The contract has only `absent` and `version` conditions. That covers what `session` does:

| Need | How | Tested |
| --- | --- | --- |
| Create once | `absent` | yes |
| Exchange lock | a put with `absent` and a short `expires_at`. An item past its expiry is absent to a condition, so no "or expired" clause is needed | A 400 ms lock is taken once, refused for the second taker, free again after 600 ms |
| Logout token replay | `absent` | A second claim of one `jti` fails |
| Idle refresh | a put under the `version` that the check read | Eight concurrent refreshes of one version: one winner |

What does not fit is that there is no partial update. The idle refresh writes the whole value and resends the index entries, where the first spike updated one attribute. The driver also reads every key it touches (strongly consistent `BatchGetItem`) before it writes, even for a single conditional put. So a refresh is 2 DynamoDB calls, 1 more read unit and 2 write units for a 2 KB item, and about 1.1 ms against 0.5 ms here, which the check pays inline in the request that finds it due (at most once a minute for each session). Options for the first version: accept it, or do the refresh after the allow answer has been returned (not possible on the Lambda authorizer, which must finish before it returns). Nothing in the contract blocks either.

A smaller point: the driver logs every refused condition as one `WARN refused method=Transact code=aborted message=version` line through `log/slog`'s default logger. A lock that is taken or a refresh that loses the race is normal, and each makes a line. `session` should set the default logger or a handler that drops these.

**2.3.3 Expiry: fits.** `expires_at` is set by the caller and enforced by the driver on read: past it the item is absent to `Get`, `Query` and conditions. Tested: a session with a 1.1 s lifetime is absent at 1.3 s. DynamoDB's TTL frees the space later. The idle lifetime is `session`'s own, from the readable header, as the design says. An item that is idle-expired stays in the table until its absolute `expires_at` (up to 8 hours), as in the first spike.

**2.3.4 Linearizable reads: fit, with one trap.** `Get{linearizable: true}` is `ConsistentRead`, and the check is exactly one `GetItem` (asserted in the test). The default of the flag is `false`, an eventually consistent read, so a forgotten flag silently weakens the logout guarantee. `fit.Store` sets it on every read. A conformance case in `session` should assert it. DynamoDB Local cannot show the difference.

**2.3.5 Call deadlines and the correlation id: fit.** Tested through the in-memory transport:

- A caller's deadline of 800 ms reaches the handler as `Connect-Timeout-Ms: 799`, and the correlation id arrives (`corr-42`). The in-memory mount must have `call.Inherit` around the handler and the client `call.ClientOptions()`, as the in-process page says; without them the id is lost.
- A store made slow by 400 ms and a deadline of 60 ms: the call returns after 60 ms with `deadline_exceeded`. The deadline reaches the AWS SDK call.
- A store made slow by 3 s, through `Core.Check` with its 1.5 s limit: 503 after 1.5 s (fails closed).
- A failing engine: code `unavailable`, reason `engine`, and the message is only that. The DynamoDB text is in the journal, which is what the contract promises. `session` maps every code but `not_found` to 503.
- Go sets no default deadline for a call, so the core's own limit stays. The driver's `Transact` retries a lost race up to eight times with a growing wait, and the AWS SDK retries on its own. Both are bounded by the caller's deadline only.

**2.3.6 Key port: does not fit as it stands.** The purposes of the key port are a closed list, and each has one algorithm ([key/docs/algorithms.md](https://github.com/truvity/atoom/blob/94ab004a41171fd74f8c9c37bbb832595324d6dc/key/docs/algorithms.md), "What each driver holds, today"). `session` needs a key for the `private_key_jwt` client assertion and one for the signed identity header. Tested on `key/software`: `Ensure("client-assertion", ES256)` and `Ensure("session-client-key", ES384)` are refused (`invalid_argument`, reason `purpose`), and `token-signing` with `ES256` is refused (`failed_precondition`, reason `algorithm`). `ES256` exists only for the purpose `audit-log`. The spike used `token-signing` with `ES384` as a stand-in and verified the assertion with go-jose. 172 µs per signature through the in-process port (software driver, 500 signatures). Two consequences:

- The planned change in atoom, "the key port takes any purpose a host declares", is a requirement for `session`, not a nicety. Until then the stand-in works with Keycloak if its client accepts `ES384` (not run in this spike: no Keycloak).
- The port returns an ASN.1 DER signature and a JWS wants the raw `r||s`. The 10-line conversion is in `fit.Signer.Assertion`. Whoever writes the JOSE helper in `session` needs it.
- `key/awskms` was read, not run: it takes a KMS client (`awskms.API`) and needs `kms:Sign`, `kms:GetPublicKey` and `kms:DescribeKey`, and `kms:DeriveSharedSecret` for `wrapping`. Its tests use a fake KMS inside atoom.

**2.3.7 Source port: fits, with naming rules.** `source/file` (Go) reads `<name>.jws` for a kebab-case name and returns the bytes unparsed. Tested: `Read("site")` returns the file and a SHA-384 version label; `if_none_match` gives `unchanged`; `Watch` saw a replaced file after 101 ms (it looks again every 200 ms). It refuses `site.yaml`, `Site`, `policy_bundle` and `../x` (`invalid_argument`, reason `schema`). So the site file must be called `site.jws` (the extension is fixed, whatever it holds), and the policy bundle `policy-bundle` (no underscore). A document is limited to 4 MiB. The driver is meant for signed documents. A plain YAML site file works but is named like a signed one.

**2.3.8 Not on master yet.** The `seal` block, the Cedar loader with its decision test set, the `durability` field of `Capabilities` (the test prints `store=dynamodb tail_log=false` and no durability), and `Atoom-Correlation-Id` as named in 0006 (the in-process page uses the `call` package, which carries it). Limits that the test printed: a value of 390 KiB is refused (`invalid_argument`, reason `batch`; the limit is 380 KiB), a key with a space is refused (reason `address`).

**2.3.9 Packaging.** `go get` of each atoom module at the commit gives a pseudo-version, and the repository is public, so no `replace` and no vendoring is needed. `source/file` has no tag at all. atoom ships no Go helper for the in-memory transport: the 25 lines are copied into `internal/fit/memnet.go`, and `session` will have its own copy until atoom adds one ([socket/docs/in-process.md](https://github.com/truvity/atoom/blob/94ab004a41171fd74f8c9c37bbb832595324d6dc/socket/docs/in-process.md): "No Go helper is provided").

## 3. Item 2: authorizer events through the Lambda Web Adapter

### 3.1 Method

The emulator image is `provided.al2023` with the adapter as `/opt/extensions/lambda-adapter` and `spike/cmd/fitapp` as `/var/task/bootstrap` (`spike/lwa/Dockerfile`, `spike/lwa/run.sh`). `fitapp` is the check core behind a plain HTTP server on port 8000 with the first spike's authorizer shapes. It logs how each request arrived (HTTP request, or the pass-through path `/events`; the path, which adapter headers are present, the sizes), and never a header value, a cookie or a body. The events are shaped like the AWS documentation samples (`spike/lwa/events/`). The emulator's answer and the app's log are in `spike/results/lwa-adapter.txt`. The same events went to a native Go handler (`spike/cmd/authorizer-lambda`, `aws-lambda-go`, no adapter) in the same emulator image, `spike/results/lwa-native.txt`. A third run set `AWS_LWA_ERROR_STATUS_CODES=401,503`, `spike/results/lwa-adapter-error-status-codes.txt`. One container at a time, removed at the end.

### 3.2 Results

| Event | How the adapter classified it | What the app saw | What the emulator answered | Right shape? |
| --- | --- | --- | --- | --- |
| REST API `REQUEST` authorizer, valid session | **HTTP request** (API Gateway v1 payload) | `GET /app/x?a=1`, the `Cookie` header, and the header `x-amzn-request-context` | `{"statusCode":200,"headers":{},"multiValueHeaders":{...},"body":"{...}","isBase64Encoded":false}`: the app's body inside an HTTP envelope | **No.** No `policyDocument`, ever |
| The same, no session, and the same with a failing store | HTTP request | the same `GET` | the same envelope | **No.** There is no way to return the error `Unauthorized` |

| The same, no session | Pass-through | `POST /events` | `{"isAuthorized":false}` | Yes |

### 3.3 Why: the adapter's code

The adapter does not look at authorizer events at all. It turns an event into a `lambda_http` request, and that crate decides by trying types in a fixed order.

| What | Where |
| --- | --- |
| The adapter runs `lambda_http`'s runtime. Its event type is `lambda_http::request::LambdaRequest` | `aws-lambda-web-adapter` v1.1.0, `src/lib.rs:1420` (`lambda_http::runtime_concurrent(self)`) |
| The order of the guesses: API Gateway v1 proxy request first, then v2, then ALB, then WebSocket, then VPC Lattice, and only when none parses, `PassThrough` | `lambda_http` 1.3.0, `src/deserializer.rs:30` (`ApiGatewayProxyRequest`), `:34` (`ApiGatewayV2httpRequest`), `:51` (`PassThrough`) |
| The REST authorizer event parses as `ApiGatewayProxyRequest` (observed: the event has `resource`, `path`, `httpMethod`, `headers` and `requestContext`, which is what that type wants). So it is an HTTP request | `aws_lambda_events` 1.2.0, `src/event/apigw/mod.rs:21` (`ApiGatewayProxyRequest`) |
| The HTTP API 2.0 authorizer event has `identitySource` as an array of strings. `ApiGatewayV2httpRequest` declares the field as `Option<String>` (kept for the v1 authorizer), so parsing fails and the event falls through to `PassThrough`. If `identitySource` is absent the type parses and the event is an HTTP request | `aws_lambda_events` 1.2.0, `src/event/apigw/mod.rs:206-207` (`identity_source: Option<String>`) |
| A pass-through event is rewritten to `POST` on `AWS_LWA_PASS_THROUGH_PATH`, default `/events` | `src/lib.rs:470` (default), `:1549-1551` (the rewrite) |
| The answer to a pass-through event is the app's body parsed as JSON and returned as it is. For an HTTP event the answer is the API Gateway response shape | `lambda_http` 1.3.0, `src/response.rs:183-189` (`PassThrough`) against `LambdaResponse::from_response` above it |
| `AWS_LWA_ERROR_STATUS_CODES` makes the adapter return an error, with a message of the form `{"statusCode":N,"body":"..."}`. No setting gives the message `Unauthorized` | `src/lib.rs:1644-1658` |
| The documentation lists non-HTTP triggers (SQS, SNS, S3, DynamoDB, Kinesis, Kafka, EventBridge, Bedrock Agents) and names no authorizer. The pass-through page lists the same | `docs/guide/src/introduction.md:20`, `docs/guide/src/features/non-http-events.md` |

So the adapter has no mode for authorizer events. **REST API authorizer events are HTTP requests to it, always**, and nothing in its configuration changes that. **The HTTP API 2.0 case works only because `identitySource` is an array, and by a type mismatch in two crates**, not by design: a newer `aws_lambda_events` that types the field correctly, or an API Gateway that omits the field, silently makes it an HTTP request with an HTTP-shaped answer. The adapter has no test for it.

### 3.4 What could not be tested locally

- **API Gateway's reading of the answers.** The emulator hands back whatever the function returns. What API Gateway does with `{"statusCode":200,...}` where it expects a policy, or with a function error, is documented but not observed. The script's part B and A3 observe the statuses of the native shapes.
- **What the real event looks like without an identity source.** The AWS sample always has `identitySource`. Whether the field is absent or `[]` when none is configured decides whether the HTTP API case works. Part A4 of the script logs the real events with and without a source.
- **The adapter on the real Lambda service.** The emulator runs the adapter as an extension next to the bootstrap, as the adapter's own CI does (`sam local`). A real function on `provided.al2023` was not run.
- **The adapter's cost.** Not measured.

### 3.5 Result

Authorizer events cannot go through the adapter. Record [0012](decisions/0012-lambda.md) already names the fallback, and the spike confirms it is needed: **the authorizer is a native Go handler in the same binary** (`aws-lambda-go`, selected by a start-up setting), for both API Gateway products. The native handler of `spike/cmd/authorizer-lambda` answered every shape right in the emulator, including the exact error `Unauthorized` that record [0011](decisions/0011-host-adapter-rules.md) uses for "no session" on the REST API. The sign-in function stays behind the adapter. One consequence for the layers: the authorizer function has no adapter layer, only the app zip and the configuration layer.

## 4. Item 3: the real-AWS checks (not run)

`spike/scripts/aws-check.sh` is written for the maintainer. It was not run against AWS (there is no account in this spike). It was run in its dry mode, and with its apply mode against a shim in place of the `aws` command, to check its flow, its failure stop and its cleanup. The real calls are untested.

How it behaves:

- **Dry-run by default.** It prints every command it would run. `--apply` acts.
- **Only the named profile.** `--profile` and `--region` are required and have no default. It unsets the AWS credential variables of the environment and passes `--profile` and `--region` to every call. In `--apply` it prints only the last four digits of the account.
- **A name prefix on everything**, default `session-fit-<random>`, set with `--prefix`: IAM role, Lambda functions, HTTP API, REST API, DynamoDB tables, log groups. The role's DynamoDB permission is limited to tables of that prefix.
- **Everything is deleted at the end**, also when a step fails or the run is interrupted, in the reverse order. The last lines list anything with the prefix that is left.
- **It appends its output to `~/log-sluis-v2`.** Lines that start with `RESULT` are the findings.
- Needs `aws` (v2), `curl`, `jq`, `zip` and `go`.

What it checks:

| Part | Check | Open item it settles |
| --- | --- | --- |
| A1 | HTTP API status for `{"isAuthorized": false}` | design 17.1, 0011 "Open" |
| A2 | Default `authorizerResultTtlInSeconds` of an HTTP API authorizer, with the `Cookie` identity source, with none, and with 0; and whether two requests with one cookie reach the function twice | design 17.1 (HTTP API default TTL) |
| A3 | HTTP API status for a failing function, for the error `Unauthorized`, and for no cookie when the source is named | 0011 (no session is a 401) |
| A4 | The event an HTTP API authorizer receives, with and without an identity source (the field `identitySource`) | the adapter question of section 3.4 |
| A5 | Parameter mapping from `$context.authorizer.token` into `X-Session-Token`; into `Authorization` (expected to be refused); `remove:header.cookie`; what the integration then sees | design 17.1 (parameter mapping), 0011 |
| B | REST API: default TTL (expected 300), statuses for allow, deny policy, `Unauthorized`, function failure, no cookie; whether the default caches; the event | 0011 (REST default, deny is 403) |

## 6. Recommended changes to the design

For the maintainer. None is made here.

1. **Section 4 and 0012: the authorizer is a native Go handler** in the same binary. Remove "Every Lambda function runs behind the Web Adapter" from the hosts table for the authorizer, and say that the authorizer function has no adapter layer.
2. **Section 8 and 0010: use atoom's index entries for the logout lookup**, not pointer items (proposed record 0015). The tombstone read at creation stays.
3. **Section 9, session store table:** the idle refresh is a put under a version condition that rewrites the value and resends its index entries, 2 DynamoDB calls. State that a refresh costs a read unit more than the first spike's update, and decide whether it runs inline.
4. **Section 9, rules:** every read passes `linearizable: true`, and a conformance case asserts it.
5. **Section 9 and 0006, keys:** the purposes of the key port are a closed list today. Add to what `session` needs from atoom: purposes for the client assertion and the identity header (named by `session`, declared to the port), and `ES256` or `ES384` for them. Until then `token-signing` with `ES384` is the stand-in.
6. **Section 10, site file:** the file driver serves `<name>.jws`. Name the site file `site.jws` and the bundle `policy-bundle`, or decide whether `session` signs its site file.
7. **Logging:** `session` configures `log/slog` so that the driver's one WARN line for each refused condition is not a log line for each lost race.
8. **Section 16, item 1:** mark the fit spike done, with the three items open that need an account (section 4).

## 7. Proposed new records

For the maintainer to accept or drop. This spike changed no record.

**0014. The authorizer is a native Go handler.** Context: the fit spike showed that the Lambda Web Adapter takes a REST API authorizer event for an HTTP request and answers in the HTTP shape, and takes an HTTP API 2.0 authorizer event for a pass-through event only because of a type mismatch. Decision: the authorizer function of both API Gateway products is a native Go handler (`aws-lambda-go`) in the same binary as the HTTP server, chosen by a start-up setting. It has the app zip and the configuration layer and no adapter layer. The sign-in function stays behind the adapter. It resolves the open case of 0012 and its roads-not-taken row "A native handler for the authorizer from the start" (the spike decided). Consequence: two entry points in one binary, tested with the same sample events (the unit tests of the first spike already call the handlers).

**0015. Logout through atoom's index entries.** Context: [0010](decisions/0010-logout-pointer-items.md) builds pointer items to get a consistent lookup. atoom's `store` port gives index entries written in the item's transaction, with a linearizable `Query`. Decision: each session item carries index entries for `sid` and for subject; a back-channel logout is a linearizable `Query` by entry and one `Transact` of deletes; the tombstone, read once at creation, stays. Pointer items are not built. Consequence: no read-modify-write at sign-in (64 tries against 16 for sixteen parallel sign-ins of one subject), no 400 KB bound on the set, a logout that is a `Query` and a `BatchGetItem` instead of one `GetItem`. Reverses the 0010 decision "pointer items" and its consequence about the item size. Needs the real service to confirm that the linearizable query sees a session committed a moment before (the driver documents it; DynamoDB Local cannot show it).

## 9. How it was run

Run the commands from the `spike/` directory. `CGO_ENABLED=0` as in the first spike. At most one container at a time.

```sh
export CGO_ENABLED=0
# DynamoDB Local, pinned by digest
docker run -d --rm --name ddb -p 127.0.0.1:18000:8000 \
  amazon/dynamodb-local@sha256:6ada631ec7aa5fc83446855eb17233e3dad184fec47477e8140c6c569cfe0c86 \
  -jar DynamoDBLocal.jar -inMemory -sharedDb
go test ./internal/fit -v -count=1          # the contract tests; skipped when DynamoDB Local is not there
go run ./cmd/fitbench 3000 5                # the latency tables
docker stop ddb

lwa/run.sh                                                   # authorizer events through the adapter, in the emulator
lwa/run.sh -e AWS_LWA_ERROR_STATUS_CODES=401,503             # with error status codes
MODE=native lwa/run.sh                                       # the native Go handler, no adapter

scripts/aws-check.sh --profile NAME --region REGION          # dry run
scripts/aws-check.sh --profile NAME --region REGION --apply  # the real run, by the maintainer
```
