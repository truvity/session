# Spike of 2026-11-18

Status: findings of the first spike. Throwaway prototype code is in [spike/](../spike/). Nothing here is production code and nothing was deployed.

The spike followed the "Next steps" of [the design](design.md). It ran on one shared Linux machine, with at most two containers at a time, against containers only: Keycloak 26.8, DynamoDB Local (`amazon/dynamodb-local:latest`), Envoy v1.34 and nginx 1.27. No call went to any real issuer or to AWS. How the pieces were started is in [spike/scripts/run.md](../spike/scripts/run.md).

## 2. Item 1: the check service

The prototype is `spike/internal/sess` (`flow.go`, `store.go`, `core.go`) with the entry point `spike/cmd/spike`.

What was run against Keycloak, through Envoy, with a scripted browser (`spike/cmd/e2e`, no headless browser):

| Step | Observed |
| --- | --- |
| Top-level navigation without a cookie | 302 to `/_session/login?return_to=...` |
| `/_session/login` | Stores the transaction (state, nonce, PKCE verifier, return path) in DynamoDB. Posts a PAR request with a `private_key_jwt` client assertion (ES256). Redirects to the issuer with only `client_id` and `request_uri`. Sets the short-lived binding cookie |
| Issuer | Keycloak was set to refuse authorisation requests that are not pushed. A direct request was refused: "Pushed Authorization Request is only allowed". Good: the PAR rule is enforced by the issuer, not only by us |
| `/_session/callback` | The issuer's redirect carried `code`, `state`, `session_state` and `iss` (RFC 9207). The callback checks the binding cookie, `state` and `iss`. Exchanges the code with the verifier and a new client assertion, validates the ID token with `go-oidc` (signature, issuer, audience, expiry) and the nonce, creates the session under a new id, sets `__Host-spike` and clears the binding cookie |
| Cookie | `__Host-spike=<id>; Path=/; HttpOnly; Secure; SameSite=Lax`, no `Domain` |
| Store | One item per session. Key is `HMAC-SHA256(id)`. The record is AES-256-GCM with the id as associated data. Unit tests show that the stored key does not work as a cookie, and that a record copied under another id does not open |
| Logout POST | 403 without the CSRF header, 403 with `Sec-Fetch-Site: cross-site`, 302 to the issuer's end-session with `id_token_hint` and the cookie cleared when the headers are right |
| Back-channel logout | Keycloak's admin "logout user" posted a logout token to `/_session/backchannel-logout`. The check validated it, claimed the `jti`, deleted the session through the index. The next request got 401 |
| `return_to` | Only a path that starts with one `/` is kept. `//evil.test` becomes `/` |
| Store down | The check answers 503 after the 1.5 s timeout (see 3.4) |

Things that were not done: refresh of the sign-in access token, the RFC 8693 exchange client, `jwks` publication, the identity header (option C). The lock and the `jti` claim exist as store functions with unit tests.

Findings:

- Keycloak's client needs `use.jwks.string`, a JWKS in `jwks.string`, `token.endpoint.auth.signing.alg` and `require.pushed.authorization.requests`. The assertion `aud` was the realm issuer URL, and Keycloak accepted it.
- Go's `net/http/cookiejar` will not send a `Secure` cookie over plain HTTP. The scripted browser keeps cookies by hand. Real browsers treat `http://localhost` as a secure context, but the conformance suite should use TLS (or a browser) and not a Go cookie jar.
- DynamoDB expressions have reserved words. `keys` is one: a first version of the pointer item failed with "Attribute name is a reserved keyword". Use `ExpressionAttributeNames`.

## 3. Item 2: host proxies

All three hosts were driven with the same script (`spike/cmd/e2e checks`). The check service has one core and three adapters (`spike/internal/sess/adapters.go`): HTTP (Envoy and nginx), gRPC (Envoy, `ext_authz` v3 from `go-control-plane`).

### 3.2 Envoy

- Redirect against 401: both work. In HTTP mode the deny answer's `Location` and `Content-Type` reach the browser only because they are listed in `allowed_client_headers`. A deny answer with a body works in both modes. A 503 answer from the check keeps its status in both modes, but in HTTP mode the body of that answer was empty.
- Headers set by the allow answer reach the upstream in both modes. In HTTP mode only the names in `allowed_upstream_headers` are copied. In gRPC mode the check sends `headers` (overwrite) and `headers_to_remove`.
- **Header stripping differs between the modes.** The HTTP answer cannot say "remove this header". Setting it to an empty value makes Envoy send an empty header to the upstream. That neutralises a spoofed value but leaves an empty `Authorization` and `Cookie` on the request, and some upstreams treat an empty `Authorization` as an error. The gRPC answer removes the header. The design says the host strips and the allow answer sets (S8). For Envoy HTTP mode this needs a route-level `request_headers_to_remove`, or an allow answer that always sets every owned header.
- `Cookie` rewrite works in both modes: the allow answer replaces the whole `Cookie` header, so the session cookie never reaches the upstream.
- `Set-Cookie` on refresh works in both modes. HTTP mode needs `allowed_client_headers_on_success`. gRPC uses `response_headers_to_add` with an append action, which allows several cookies.
- The check sees only the headers listed in `allowed_headers` (the field `authorization_request.allowed_headers` is deprecated in v1.34 and the validator warned about it). The spike lists `cookie`, `accept`, `sec-fetch-mode`, `sec-fetch-site` and `origin`. The conformance suite must fail if a host forgets one: without `sec-fetch-mode` every navigation becomes a 401.
- Path normalisation: with `normalize_path: true`, `merge_slashes: true` and `path_with_escaped_slashes_action: REJECT_REQUEST` on the connection manager, the check receives the same path the router uses.
- The per-route switch `ExtAuthzPerRoute disabled: true` is what keeps `/_session/` out of the check.
- Envoy's `status_on_error` (set to 503) is what a client sees when the check cannot be reached. `failure_mode_allow: false` is the default and was kept.

### 3.3 nginx

- `auth_request` accepts only 2xx, 401 and 403 from the check. Any other status becomes a 500 for the client. So the check's 503 for "store down" shows as 500: the request is still refused (fails closed) but the status differs from the Envoy hosts.
- A 302 from the check is not understood either. The nginx adapter answers 401 plus `X-Session-Action: redirect` and `X-Session-Location`. nginx turns that into a 302 in a named location. The JSON 401 body has to come from nginx. The example config must therefore carry the `login_required` body.
- Allow headers travel through `auth_request_set` and `proxy_set_header`. An empty variable makes nginx drop the header, so setting every owned header on every request strips spoofed values cleanly.
- `Set-Cookie` travels through `$upstream_http_set_cookie`, which holds only the first one.
- **Path confusion, reproduced.** With `proxy_set_header X-Original-URI $request_uri`, the check sees `/assets/../private/x`, treats it as the public `/assets/` prefix and allows it with no session. nginx then proxies the raw URI, `/assets/../private/x`, to the upstream, which may normalise it to `/private/x`. This is the threat the design lists ("path confusion between proxy and check"). With `$uri$is_args$args` (nginx's normalised and decoded path) the check sees `/private/x` and denies. The nginx example must use the normalised form, and the conformance test for dot-segments and encoded dots must run against nginx too. Note that `$uri` is decoded: encoded slashes (`%2F`) need a decision (reject them, as Envoy's `REJECT_REQUEST` does).

### 3.4 Fail closed and timeouts

The check puts a 1.5 s timeout on its store calls (the AWS SDK has no short default). Without it, a paused store made the check hang until Envoy's own timeout (2 s) fired. Both give 503 on Envoy. Set the proxy timeout above the check's own timeout, so that the check's 503 is the one the client gets.

## 4. Item 3: Lambda authorizer

Code: `spike/internal/sess/lambda.go`, tests in `lambda_test.go`. The handlers were called with sample events shaped like the AWS documentation. The Lambda runtime interface emulator was **not** run, and nothing went to AWS.

What the code does:

- REST API `REQUEST` authorizer (also HTTP API payload 1.0): reads `Cookie` from the event headers, answers an IAM policy with `principalId` and a `context` map (`sub`, `email`, `groups`). No session gives the error `Unauthorized` (401). Store down gives a plain error (500, fails closed).
- HTTP API payload 2.0 with simple responses: the cookies are in a separate `cookies` array, not in `headers`, so the handler joins them. Answer is `{isAuthorized, context}`.
- A second Lambda handler for the sign-in paths (`SignInHandler`): wraps the same `http.ServeMux` for an HTTP API proxy integration (payload 2.0). `Set-Cookie` lines go in the response `cookies` array. The real logout handler answered 403 through it without the CSRF header. The login and callback routes need the issuer and were not run through the Lambda shape.

What reaches the integration (AWS documentation, not measured):

1. Only `principalId` and the `context` map. The map may hold strings, numbers and booleans, "you cannot set a JSON object or array" as a value in the REST API documentation (Output from an API Gateway Lambda authorizer). The HTTP API page shows an array and a map in `context` in its examples, so the two products differ.
2. The integration gets them as `$context.authorizer.<key>`: REST API mapping templates, HTTP API parameter mapping, or in the event of a Lambda proxy integration (`requestContext.authorizer.<key>`).
3. The authorizer cannot change the request or the response. It cannot set or remove a header, and cannot send `Set-Cookie` or a `Location`. The browser's own headers go to the integration unchanged unless the integration's parameter mapping overwrites or removes them. So S8 on API Gateway is done by the integration configuration, not by the allow answer.
4. HTTP APIs reserve some headers in parameter mapping: "The following headers are reserved. You can't configure request or response mappings for these headers", and the list includes `Authorization`, `Origin`, `Forwarded`, `X-Forwarded-*` and `Via`. `Cookie` is not on the list. So on an HTTP API the check cannot strip or set `Authorization` by mapping. The per-API token (exchange mode) would have to travel in another header name, and the site must ignore a browser-sent `Authorization`. This is a design consequence, to be checked in a real account.

Status codes (documentation):

| Case | REST API | HTTP API |
| --- | --- | --- |
| Identity source named, and missing, null or empty | 401, and the Lambda is **not invoked** | 401, and the Lambda is not invoked |
| The function returns the error `Unauthorized` | 401 ("the authorizer function returns a `401 Unauthorized` HTTP response" in the REST example) | `{"errorMessage":"Unauthorized"}` gives 401, "don't specify any identity sources" in that case |
| Deny policy | 403 | The page does not state the status for `isAuthorized: false`. Verify |
| Function error or invalid response | 500 | 500 |

So for S4 the authorizer should return the error `Unauthorized` for "no session" (401), not a deny. Naming the `Cookie` header as the identity source gives a free 401 for requests without any cookie, but it also makes API Gateway skip the function, which is fine, and it makes `Cookie` part of the cache key.

Caching and logout, from the documentation:

- REST API: "If this field is not set, the default value is 300. The maximum value is 3600" and "If it equals 0, authorization caching is disabled" (CreateAuthorizer API reference). **So the REST API authorizer caches for 300 seconds unless the TTL is set to 0 explicitly.** The design says "the authorizer does not cache its answers by default" (section 4). That is wrong for REST APIs. The Helm and IaC examples must set `AuthorizerResultTtlInSeconds: 0` and a test must check it.
- HTTP API: caching is controlled by `authorizerResultTtlInSeconds`, "If it equals 0, authorization caching is disabled", maximum 3600, and "To enable caching, your authorizer must have at least one identity source". The page does not state a default value. Set it to 0 explicitly here too.
- Cache key: the identity sources. With the `Cookie` header as the source, "if a client specifies the same parameters in identity sources within the configured TTL, API Gateway uses the cached authorizer result". A back-channel logout deletes the session in DynamoDB, but a cached allow stays valid until the TTL ends: logout lags by up to the TTL (300 s by default on REST, up to 3600 s). A logout from the browser's own POST would be seen only after the cookie is cleared, but a stolen cookie keeps working for the TTL.
- With caching on and a policy `Resource` that names one method ARN, the cached policy is reused for other routes. The REST documentation says "Ensure that your policy is applicable to all resources and methods across your API", and the HTTP API page says that by default the cached response applies to all routes of the API and that `$context.routeKey` can be added to the identity sources. The prototype uses the method ARN and assumes no cache.
- Other cookies change the key: the identity source is the whole `Cookie` header, so a changed `theme` cookie is a cache miss. A cache hit rate depends on that.

Recommendation: keep caching off, as decided in decision 0012 (Q6), and state in the guide that the default of the REST API is on. Optionally allow a few seconds (5 to 10 s) for sites with a high rate and document the lag.

## 5. Item 4: DynamoDB

**All numbers below come from DynamoDB Local (a Java process on the same host, in memory). The real DynamoDB service was not measured. Real latency includes a network round trip to the service, in the same region typically a few milliseconds per call; do not read the numbers below as service latency.** They are useful for relative cost (how many calls, how much work in the check) and to show that the code itself adds little.

Method: `spike/cmd/bench`, one connection, sequential, 50 warm-up calls, then 1000 calls (250 for the writes that create items). The machine was lightly loaded (load average about 1). Session record about 1.7 kB with a 1.5 kB token. Times in milliseconds.

The "Create + logout" rows include the creation. Two runs were made (Envoy up, then nginx up, so that two containers ran at a time); the raw outputs are in [spike/results/](../spike/results/), together with the output of the proxy checks. Between runs the same operation moved by 10 to 20 percent, so read the numbers as orders of magnitude.

What the numbers say:

- The check's own work (decrypt, decision, adapter, one proxy hop) is about 0.1 to 0.3 ms on top of the store call. The store call dominates, so the real service's latency decides whether the "no local cache" decision (0012 Q2) is fine.
- A strongly consistent read costs nothing extra on DynamoDB Local. On the real service it costs twice the read units of an eventually consistent one (below) and may cost latency; not measured here.
- The idle refresh at most once a minute keeps the write path off almost every request. With eight concurrent refreshes of the same session, exactly one conditional update won (unit test).

Cost, by arithmetic from the DynamoDB documentation ("Capacity unit consumption for read operations"): a strongly consistent read of an item up to 4 KB is 1 read unit, an eventually consistent read is 0.5, and a read of an item that does not exist still consumes read throughput. A session item is below 4 KB, so a check is 1 read unit. The tombstone check adds a BatchGetItem of two tombstone keys, "DynamoDB processes each item in the batch as an individual GetItem request", so with strong consistency it adds 2 read units: **3 read units per check instead of 1**. A conditional UpdateItem of a 2 kB item is 2 write units, at most once a minute per active session. A transactional write costs two write units per item, so a session created with two pointer items costs about 8 write units for a 2 kB session (the session item 2 KB and each pointer item under 1 KB, each doubled), against 2 for a plain put.

### 5.1 Logout and the tombstone (design Q2)

The race in Q2: a back-channel logout looks up sessions in a secondary index. Global secondary indexes are eventually consistent (design Q2 says so). A session created a moment before the logout may not be in the index yet, and the logout deletes nothing.

Tested on DynamoDB Local (`internal/sess/store_test.go`):

- **Index lag cannot be reproduced on DynamoDB Local**: its secondary indexes are updated synchronously. The test creates the lag by ordering. The logout writes the tombstone and queries the index, then a session with a creation time before the logout is written, which is what a lagging index looks like.
- Without the tombstone check, that session stays readable and valid. With the check (the tombstone for the `sid` and for the subject is read together with the session, and a session not newer than the tombstone is refused and deleted), it is refused. A later sign-in of the same person (new `sid`) is not affected. A subject tombstone (logout token without `sid`) refuses older sessions and lets newer ones live.
- Creation times are in milliseconds. Whole seconds would refuse a sign-in made in the same second after a logout.

Result: the tombstone idea (option B) is correct. Its cost is the extra read per check (3 read units against 1, and a second round trip because the tombstone keys come from the session record: 0.46 ms against 0.24 ms here). It has to be read on every check, because a lagging session can be checked long after the tombstone was written, and the tombstone must live as long as such a session could (up to the maximum session lifetime, not "a short time").

**Option C, tested as a variant: pointer items, no secondary index.** Each session creation writes, in one transaction, the session and two pointer items `P#sid#<iss>|<sid>` and `P#sub#<iss>|<sub>`, each holding a set of session keys. The logout reads the pointer with a strongly consistent GetItem and deletes the sessions listed. A strongly consistent read of a base-table item cannot miss a session that was committed before it. What remains is one race: a logout that arrives before the sign-in has finished. The callback closes it with one tombstone read **at session creation**, not on every check, and ends the session it just made if a tombstone newer than the start of the sign-in exists (tested, `TestPointerItemsLogoutBeforeSignInFinished`). Costs: sessions cost about four times the write units to create (the transaction, three items), a check costs 1 read unit and one round trip, and the logout costs one GetItem plus the deletes. The pointer set grows with the number of sessions of one subject, within the 400 KB item limit, and has to be pruned when a session ends or expires (TTL on the pointer item covers the maximum lifetime, a stale member costs one failed delete).

Recommendation: C. It makes the per-request path as cheap as it can be (one strongly consistent GetItem), needs no secondary index (so no index cost, no index lag, simpler IAM and table), and puts the extra cost on sign-in and logout, which are rare. Keep the tombstone, but read it only at creation. If the pointer set size is a concern for a subject with many sessions, use a sort key (`pk = P#sub#...`, `sk = session key`) and a strongly consistent Query. That form was not built.

## 7. E8: does sluis v1 accept the proxy's sign-in token as a subject token?

Source: `github.com/truvity/sluis`, branch `master`, commit `2057194b1` (release v1.85.0), read-only clone. No live call was made.

**Answer: no for a confidential client, which is what the design gives `session` (`private_key_jwt`). The only way in v1 is to register `session` as a `public` client with `sign_in_exchange: true`, which defeats S3 and cannot use PAR.**

The v1 feature is called `sign_in_exchange`. What it accepts, by code:

| What | Where |
| --- | --- |
| The subject token must be the access token of a live sign-in, never an ID token | `internal/issuer/storage.go:3088` (`signInProof`), `:3092-3096` (`wrong_token_type`) |
| The token must be one the issuer recorded, and its client must declare `sign_in_exchange` | `storage.go:3099-3111` (`no_record_of_token`, `sign_in_not_exchangeable`) |
| It must be presented by the client it was issued to | `storage.go:3113-3117` (`presented_by_another_client`) |
| The subject must be a person; the session must be live; agent-class, recovery and conformance sessions are refused | `storage.go:3119-3151` |
| `sign_in_exchange: true` is refused at policy load on any client that is not `public` | `policy/policy.go:1217-1219` ("only a public client, a CLI, may trade its sign-in"); the field is documented at `policy/policy.go:615-624` |
| `session: agent` together with `sign_in_exchange` is refused | `policy/policy.go:1243-1247` |
| The target audience is decided by the target client's `requires`, one audience per exchange | `storage.go:2979-2990`, `:3000-3008` |
| Documentation of the same rule | `docs/concepts/sluis/trust.md:27`, `docs/concepts/sluis/verify-and-issue.md:55-59`, `docs/reference/sluis/policy-clients.md:32` |

What this means for `session`:

- `session` as designed is a confidential client with `private_key_jwt`. v1 refuses `sign_in_exchange` on it at load. So its sign-in token cannot be a subject token. **E8 fails** for the design as written.
- v1 has no `private_key_jwt` at the token endpoint at all: `AuthMethodPrivateKeyJWT: false` (`internal/issuer/provider.go:59`) and a client's method is only none or Basic (`internal/issuer/client.go:51-62`).
- v1 has no PAR: `request_uri` is refused with `request_uri_not_supported` (`internal/issuer/surface.go:106-108`), and `docs/concepts/sluis/not-served.md:29` lists PAR as not served.
- The exception: a `public` client with `sign_in_exchange: true` and PKCE works, and the exchange accepts its access token for another audience, gated by the target's `requires`. For `session` that would mean no client authentication at all and no PAR, and the access token would be exchanged as a bearer by whoever holds it together with the client id (the issuer only checks the presenting client id for a public client, `storage.go:3113-3117` and `:763-770`). That is the CLI model (`sluisctl`), not a web service's. Not recommended.
- The refresh path of a public client's sign-in is as for the CLI (`lifetimes.refresh`). Back-channel logout is available per client (`policy/policy.go:642`), but the docs note it is unusable behind oauth2-proxy (`docs/reference/sluis/policy-clients.md:36`).

So sites on v1 wait for v2, as decision 0007 foresaw for the "no" case. Nothing in v1 needs to change for the design to proceed on Keycloak. The question for v2 is the same: its exchange must accept an access token of a confidential `private_key_jwt` client as subject token, bound to the presenting client.

## 8. Recommended changes to the design

1. **Section 4, API Gateway: the authorizer does cache by default on REST APIs** (300 s unless the TTL is 0). Change "does not cache its answers by default" to "must be configured with TTL 0". Add a test to the examples. State that the HTTP API page does not give a default.
2. **Section 4 and S8: header stripping on API Gateway is the integration's job**, and HTTP API cannot map `Authorization`. Say so, and say which header carries the per-API token there.
3. **Section 4, S4: for "no session", the authorizer returns the `Unauthorized` error (401), not a deny** (403).
4. **Section 4, nginx row and S4**: `auth_request` cannot pass a 302 or a body, and turns any other status into 500. Document the 401 + marker pattern. Fail-closed on nginx shows as 500, not 503.
5. **Section 4 rules, S8**: in Envoy HTTP mode, a removal can only be an empty value. Prefer gRPC mode where the answer has `headers_to_remove`, or add `request_headers_to_remove` to the route, or always set every owned header.
6. **Threat model, path confusion**: the check must receive the normalised path, and the conformance suite must run the dot-segment and encoded-dot cases on every host. Reproduced on nginx with `$request_uri`. Ship the `$uri$is_args$args` form, reject encoded slashes, and on Envoy ship `normalize_path`, `merge_slashes` and `path_with_escaped_slashes_action`.
7. **Q2 (section 16)**: choose **C with a creation-time tombstone check** over B. B is correct but triples the read units of every check. C keeps the per-request path at one strongly consistent read. Section 9's table rows "Back-channel logout" and "Token cache" change accordingly: pointer items replace the secondary index.
8. **Section 9, store port**: add a store timeout to the port contract (the check needs a bounded wait to fail closed in time) and make sure the proxy timeout is longer than the store timeout.
9. **Creation time in milliseconds** in the session record, for the tombstone comparison.
10. **Section 12 and decision 0007, E8**: record the answer: no in v1 for a confidential client, with the reasons above. Add "sluis v2 must accept a `private_key_jwt` client's access token as a subject token, presented by the same client" to what we ask of v2.
11. **Envoy examples**: the per-route `ExtAuthzPerRoute disabled: true` for `/_session/`, `allowed_headers` including `sec-fetch-mode`, `sec-fetch-site`, `origin`, and `allowed_client_headers` for `location` and `content-type` (HTTP mode). The `authorization_request.allowed_headers` field is deprecated in v1.34; use the top-level `allowed_headers`.
12. **Conformance suite**: do not use a Go cookie jar with `Secure` cookies over plain HTTP. Use TLS or a browser.
